# Порядок ведения Git в FeeArb

## Ответственный

- Единственный автоматизированный автор изменений в этом checkout — Codex.
- Другой агент или автоматизация может писать в репозиторий только по прямому указанию пользователя.
- Codex не предполагает, что незнакомые изменения можно удалить или присвоить своей задаче: сначала определяется их происхождение и назначение.

## Перед началом каждой задачи

1. Выполнить `git status --short --branch`.
2. Просмотреть последние коммиты и diff затрагиваемых файлов.
3. Отделить уже существующие изменения пользователя от новой задачи.
4. Проверить, что runtime-состояние, логи, базы, секреты и сборочные артефакты не попадут в коммит.

Если в рабочем дереве есть чужие или не относящиеся к задаче изменения, Codex сохраняет их и работает вокруг них. Сброс, перезапись и удаление без отдельного разрешения запрещены.

## Во время работы

- Одна независимая задача — один логический блок истории.
- Код, тесты и документация одного поведения фиксируются вместе.
- Android, backend, исследования и инфраструктурная гигиена фиксируются раздельно, если они не образуют одно неделимое изменение.
- Нельзя оставлять уже завершённую задачу незакоммиченной и начинать поверх неё следующую независимую задачу.
- Runtime-файлы не используются как способ сохранить конфигурацию в Git. Повторяемые defaults задаются в коде или шаблонах, локальное состояние остаётся игнорируемым.

## Проверка перед коммитом

Обязательный минимум:

1. Запустить тесты, соответствующие риску и затронутым модулям.
2. Выполнить `git diff --check`.
3. Добавить только файлы текущего логического блока явным списком.
4. Проверить `git diff --cached --stat` и содержимое `git diff --cached`.
5. Убедиться, что нет ключей API, токенов, `.env`, локальных URL с секретами, баз, логов, скриншотов и временных данных.
6. Создать коммит с коротким повелительным заголовком, описывающим результат.

В PowerShell после внешних команд Git, Python/pytest и Gradle обязательно явно проверять `$LASTEXITCODE`. Настройка `$ErrorActionPreference = 'Stop'` сама по себе не гарантирует остановку цепочки при ненулевом коде завершения нативной программы.

Примеры:

```text
Add bounded mobile execution timing
Harden auto-exit position trust
Add pump-cycle shadow monitor
Ignore local runtime state
```

## После коммита

1. Проверить `git status --short --branch`.
2. Если задача закончена, рабочее дерево должно быть чистым.
3. Если остались заранее существовавшие пользовательские изменения, перечислить точные пути и не смешивать их с выполненной задачей.
4. Не выполнять `push`, force-push, rebase опубликованной ветки или переписывание истории без прямой просьбы пользователя.

## Что никогда не коммитить

- `state/`, локальные SQLite/JSON state-файлы и Telegram `.sent`-маркеры;
- `logs/`, дампы и временные диагностические файлы;
- `data/` и сгенерированные исследовательские отчёты;
- `backups/`, `.bundle`, локальные ZIP-архивы;
- `tmp/`, скриншоты, UI XML и прочие временные артефакты;
- APK/AAB и другие результаты сборки, если для них нет отдельного осознанного release-процесса;
- секреты, ключи, токены и реальные файлы окружения.

## Аварийное исключение

Если срочное live-исправление нельзя безопасно разделить на небольшие коммиты из-за уже переплетённого рабочего дерева, допускается один явно названный консолидационный коммит. Перед ним обязательны полный аудит состава, расширенные тесты и документ с объяснением, почему история не могла быть безопасно разделена задним числом. После такого коммита дальнейшие задачи снова ведутся отдельными логическими блоками.
